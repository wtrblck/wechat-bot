## 原生语音支持（2026-10-28，后续轮次）

已实现原生类型 34 语音发送，区别于 WAV 文件附件。用户在手机文件传输助手确认约 1 秒的语音气泡收到且可正常播放。实际 `/send/voice` HTTP 测试完成 WAV → SILK 编码、原生构造/发送及清理，返回 `accepted:true`、`duration_ms:1000`，短时观察结束后微信仍在运行。

新增 `voice_codec.py`，使用本机安装且固定哈希的 `VoipEngine.dll` 导出，在独立子进程中编码/解码。未注入额外编码器，未使用 UI 收发或录制麦克风。输入为项目生成的非私人音频；测试编码产生 50 个 SILK 数据包、2379 字节，解码为 16000 个样本。SILK 时长依据实际解码样本数，WAV 编码后核对解码样本数，子进程超时会在开始发送前失败。

静态调用链 `0x5E09640` → `0x6CD0550` → `0x6CD09B0` → `0x6CD1BD0` 明确了构造参数。原生工厂复制 SILK 字符串到 `+0x758`，毫秒时长到 `+0x778`，元数据到 `+0x780`；使用既有调用者的元数据常量 4、3、30000 及空字符串。类型 34 通过共用发送入口完成实机播放验证。

32 项自动化测试、6 项主动调用独立进程集成测试通过，新增二进制音频含零字节的复制、时长、元数据、语音负载释放和 WAV/SILK 格式验证。请求日志只保留语音大小/哈希。当前仍限文件传输助手和校验清单内的测试文件；WAV 要求单声道 16 kHz、16-bit PCM，未支持 MP3、其他采样率或任意语音格式自动转换。

## 通用窄字符串赋值与 UTF-8 文本（2026-10-28，本轮）

此前文本只能发送 ASCII `wxbot-*` 标记且不超过 15 字节，因为 `app_thread_send.c` 的 `inline_string()` 只写 MSVC 字符串的内联缓冲区。本轮定位并核对微信自己的窄字符串赋值函数，正文和收件人都改由微信复制，不再借用探针内存。

### 定位的 ABI

| 项目 | RVA | 依据 |
|---|---|---|
| 窄字符串赋值 | `0x1F9AD0` | 入口 `56 57 53 48 83 ec 20 48 89 ce 48 39 d1 74`；`(dest, source)` 返回 dest；源容量 `< 0x10` 用内联数据，否则取 `+0` 指针；目标与源相同直接返回；长度大于目标容量时调用增长函数；否则 memmove 后写 0 结尾 |
| 窄字符串增长 | `0x03E150` | 由 `0x1F9AD0` 在长度超容量时调用；`(this, new_length, _, source_data)`；按 `max(new|0xF, capacity+capacity/2)` 计算容量，以 `0x1000` 为界切换对齐分配，复制后写 0 结尾并释放旧缓冲 |
| 宽字符串赋值（既有） | `0x9B5E0` | 与 `0x1F9AD0` 同构，容量阈值 `0x08`，元素宽度 2 字节 |

`0x1F9AD0` 有 278 处直接调用点，例如 `0x35AF58`、`0x39468B`、`0x62A6B4`，调用前把目标与全局或成员字符串分别放入 RCX/RDX，符合 `std::string::operator=(const std::string&)`。目标字符串析构仍由 `0x2010` 完成，容量 `>= 16` 时按容量释放，与赋值使用同一分配器，因此复制出来的缓冲由微信持有并释放。

## 原生环形接收、通配观察与一次未定因退出（2026-10-29）

### 环形缓冲

- `receive_test.c` 现在在同步回调里：校验向量（`span` 必须是 `0x70` 的倍数、上限 8 MiB、单次最多 32 个元素）→ 按策略过滤 → 原子 `lock xadd` 认领单调下标 → 把记录直接复制进 JS 拥有的槽位 → 最后写 `seq = index+1` 发布。槽位固定 64 个，每个 `32 + 4096 + 256 + 256 = 4640` 字节；内容上限从 512 提高到 4096 字节。
- 消费端（`probe.js`）只读取 `seq == index+1` 且未被回收的槽；`written >= next + 64` 视为已被新记录覆盖，计入 `skipped` 而不是读出撕裂数据；`content_len` 异常计入 `invalid`。事件 schema 改为 `wechat-sync-ring-1` / `wechat-send-ring-1`，并带 `ring_index`。
- 诊断计数（`capture_stats`）：`elements/unreadable/oversized/filtered/published/span_invalid/clamped`，以及最近一次向量的 `last_span_low/last_span_high/last_count`。
- 大栈帧会触发 tcc 链接 `__chkstk` 失败，因此内容不再经过栈缓冲，而是直接读进槽位；回调栈占用保持在 1 KB 以内。

### 语音编码的进程隔离修复

批量发送时语音首次返回 400：编码子进程以 `0xC0000005` 退出。定位结果是**同一进程内第二次 SILK SDK 操作会崩溃**：单独 `--inspect-silk` 正常，`--encode-wav`（编码后立即解码校验）稳定崩溃，同一进程连续两次编码也崩，而每次操作放在新进程里都正常。这是本地 SDK 的进程级状态问题，不是参数或数据问题。

修复方式是强制“一进程一次操作”：`--encode-wav` 只编码并写文件；`active_send.py` 再用第二个工作进程 `--inspect-silk <文件> --trusted` 校验哈希、解码样本数和时长。`--make-fixture` 也改为写文件后用子进程解码校验并生成 `wxbot-voice-decoded.wav`。`--trusted` 只允许项目目录内的文件（本项目的编码输出），fixture 校验仍然严格。修复后 43 项自动化测试通过，语音已重新实机验证。

## 事件归一化与重启语义（2026-10-29）

P3 要求统一事件包含会话 ID、真实发件人、方向和稳定的重启行为。这一轮先补不依赖新实机消息的部分：

- 新增 `event_model.py`：从同步元素已有的字段推导 `conversation_id`、`sender_id`、`recipient_id`、`direction`。规则保守、不做猜测：`@chatroom` 结尾的标识优先作为会话；发件人等于已配置的本人 ID 时为 `outgoing`；群会话下的其他发件人为 `incoming`；单聊中收件人是本人时为 `incoming`；其余为 `unknown`。本人 ID 只能通过 `WECHAT_BOT_SELF` 显式配置，默认不推导。
- `EventStore` 在发布事件时写入上述字段；`/health` 增加 `self_ids_configured`、`state_file`、`durable_events`、`state_restored`。
- **重启语义**：`--state-file` 把游标 `sequence` 与有界去重窗口原子写入 JSON；重启时恢复二者，因此重复消息不会再次发布。事件本身仍不持久化（`durable_events:false`），用旧游标读取会得到 `truncated:true`，而不是静默漏消息。状态文件损坏时回退为新会话（`state_restored:false`），不中断服务。
- 单元测试新增方向/会话推导、缺失字段、本人 ID 解析、跨重启去重与游标、损坏状态回退；当前 50 项自动化测试通过。

接收已接入 `media_receive.py` / `db_receive.py --media --download`，`content=[emoji]`、`media.kind=emoji`。静态 PNG/JPEG 与新 GIF 共 3 种真实入站正文经现有鉴权 `/media/ID/content` 取回，未完成时先验证 409，完成后均 ready。GIF 原始字节、全部帧、时长、MD5/HTTP SHA256 一致。单项资源 8 MiB，下载 10 秒，独立解码 12 秒；500 帧、单帧 1600 万像素、累计 1 亿像素、一轮 120 秒。网络失败退避 30 秒、最多两次尝试，其他无效资源直接失败。

收藏目录以 `kFavEmoticonOrderTable` 为准，联结 `kNonStoreEmoticonTable`。发送服务 `--emoji` 提供 `GET /emoji/favorites`、`GET /emoji/favorites/ID/content`、`POST /send/emoji`。列表不含密钥/签名，预览需同一令牌；发送只接受 request_id、recipient、emoji_id，重新核对实时收藏身份，沿用收件人策略、串行互斥和请求去重。

固定版本原生链：`0x4A1FD0` 应用任务检查点，`0x1C12A00` 消息工厂，`0x20A2800` 资源构造，`0x17A3B60` 共用发送入口。资源分配复现 `0x6977344` 的原生控制块（0x1F0、原生 vtable、引用 1/1、对象偏移 16）；字符串由微信构造函数逐项复制，资源转交消息 +0x758，类型 47，收件人仍通过本机字符串赋值函数复制。vtable 静态指针需按模块基址重定位，最初夹具发现直接比较磁盘绝对地址会因 ASLR 误拒绝，已改成相对指针核验，未跳过检查。

先通过 5 项独立进程表情夹具，覆盖卸载后异步延迟读取自有字符串、长收件人、复制身份错误拒绝、原生失败、只构造释放，每项引用清零。再在真实微信做只构造释放，确认 MD5/URL/产品标识/AES 字符串及所有权后，才从真实 HTTP 接口向原测试群和联系人各发送一次收藏表情。两边均得到 local_status=[0,0]、数据库类型 47 与服务器 ID；用户确认“两边都收到，显示正常”，已加入 `delivery-confirmations.json`。API 的 delivery_verified 仍保留 false，不将本地接受自动升级为送达。
