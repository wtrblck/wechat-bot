# 4.1.15.56 静态布局补充

日期：2026-10-28（Asia/Shanghai）。仅适用于 REPORT.md 中的 SHA256。以下是反汇编中的结构观察，**不是经过动态验证的收发 ABI**。

运行 `py -3.14 weixin-research/verify_layout.py` 可将 6 组结论的 38 个指令片段与安装 DLL 重新比对，并生成 `layout-evidence.json`。字节比对证明证据对应当前文件，不证明业务语义。

## 文本候选入口

RVA `0x55F0380` 将入口 RDX 存到 RBX，R8 存到 RSI。随后从 RDX 对应对象的 `+0` 与 `+0x20` 两个位置复制字符串形态数据到原生消息对象的 `+0xB0` 与 `+0x758`。**不能将 R8 简单认作文本指针，再按两个 C 字符串调用此入口。**

字符串复制代码读取相对 `+0x10` 的长度、相对 `+0x18` 的容量，并与 `0x10` 比较以选择内联数据或堆指针，符合 MSVC 小字符串布局的特征。字符编码、业务含义、合法容量和所有权仍未验证。

`0x55F04BD` 将消息对象 `+0x118` 写为 1；这支持一个类型字段候选，不能仅凭该常量认定已验证所有文本类型语义。

## 工厂与生命周期

RVA `0x709160` 分配 `0x7A8` 字节，控制块头部后 `+0x10` 是对象起始地址，清零 `0x798` 字节，再调用 RVA `0x77AB70` 构造函数。

返回的是写入 RCX 所指位置的双指针结构：对象指针和控制块指针。控制块的 `+0x8`、`+0xC` 存在原子增减。直接分配 `0x798` 字节再填少数字段，不能替代构造与引用计数过程。

## 接收链的不同容器

| 位置 | 静态观察 | 限制 |
|---|---|---|
| `0x2EBB760` 入口 RCX | `+0` / `+8` 提供 begin/end；计数先右移 4 位，再乘 7 在 64 位模环中的逆元 | 对齐且有效时符合 `0x70` 字节输入元素；尚未验证对象字段 |
| `0x2EBB760` 内部转换结果 | 调用 `0x2EBC830` 填充局部容器，后续迭代步长 `0x78` | 是另一个容器，不能沿用输入步长 |
| `0x38E9F80` 入口 R8 | 检查 `+0` / `+8` 空容器，主循环步长 `0x2E8` | 与前两者和 `0x798` 原生消息对象不同 |

计数公式中的常数为 `0x6DB6DB6DB6DB6DB7`，满足 `7 * constant mod 2^64 = 1`。该公式是静态推断；只有在 begin/end 差值合法且满足对齐约束时，才能解释为元素个数。

后续读取接收消息前，必须先确认选中的 Hook 实参到底是哪一种对象，再验证其中的字符串、消息 ID 与发送者字段，不能跨函数复用偏移。

## 本机 Frida 兼容性记录

独立测试进程上，Frida 17.24.3 的 `Process.mainModule` 返回了 `KERNEL32.DLL`，而测试 EXE 仍可按名称找到。本轮改为通过 Windows `QueryFullProcessImageNameW` 检查目标进程，通过名称查模块，再核对加载路径、文件哈希和内存入口字节。

这只说明此次环境下不能依赖模块枚举顺序，**没有证明它是此前微信退出的原因**。

API 依据：[Frida JavaScript API](https://frida.re/docs/javascript-api/)。

## 后续动态验证补充

原生回调已在实机解析 filehelper 测试消息。`0x2EBB760` 的 RCX 为 `0x70` 步长容器；元素 `+0x8`、`+0x18`、`+0x20` 分别通过子对象 `+0x8` 的 MSVC 字符串指针读到发送方、接收方、正文，`+0x14` 为类型，`+0x48` 为时间戳，`+0x50` 为 64 位消息 ID。当前仅在本人手机到 filehelper 的文本同步中匹配，不代表所有消息类型均可使用这些语义。

`0x1808560` 的 R8 指向发送任务智能指针。任务 `+0x8` 保存原始消息，`+0x18` 保存转换后的 `0x2E8` 数据库对象。对原始消息 `+0xB0` 和 `+0x758` 的读取已匹配真实手动发送的 filehelper 与 `wxbot-send-final-1028`；不能把这些偏移套在任务自身或数据库对象上。

这些观察仍没有验证主动发送 ABI，尤其没有验证对象构造、调用线程或异步成功结果。

## 窄字符串赋值（2026-10-28 补充）

`0x1F9AD0` 是当前模块里 `std::string` 的赋值/复制函数，与宽字符版本 `0x9B5E0` 同构，已用于替换只支持内联短串的写入方式。

| 项目 | 窄字符串 | 宽字符串 |
|---|---|---|
| 入口字节 | `56 57 53 48 83 ec 20 48 89 ce 48 39 d1 74` | `56 57 53 48 83 ec 20 48 89 ce 48 39 d1 74` |
| 参数 | `(rcx=dest, rdx=source)`，返回 dest | 相同 |
| 内联判据 | 源容量 `< 0x10` | 源容量 `< 0x08` |
| 结尾写入 | 1 个 0 字节 | 1 个 0 字 |
| 增长函数 | `0x03E150` | `0x9A9B0` |

`0x03E150` 的形参是 `(this, new_length, unused, source_data)`：按 `max(new|0xF, capacity+capacity/2)` 求容量；`< 0x1000` 时直接分配 `capacity+1`，否则分配 `capacity+0x28`、把指针向上对齐 32 字节并把原始指针写回 `-8`；复制后写 0 结尾，旧缓冲容量 `>= 16` 时释放。这与 `0x2010` 析构函数的判定一致，所以复制出来的缓冲可以安全交给微信对象持有。

`0x1F9AD0` 有 278 处直接调用点，例如 `0x35AF58`、`0x39468B`、`0x62A6B4`，调用前分别把目标与全局/成员字符串放入 RCX/RDX。静态与动态证据都不支持把它看成某个子系统的专用函数。
